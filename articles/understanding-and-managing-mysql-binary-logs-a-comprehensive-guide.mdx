<p>When working with <strong>MySQL</strong>, especially in production environments, understanding <strong>binary logs (binlogs)</strong> is essential. Binary logs record all changes to the database, such as <code>INSERT</code>, <code>UPDATE</code>, and <code>DELETE</code> statements, and are primarily used for <strong>replication</strong> and <strong>point-in-time recovery</strong>. This guide will walk you through everything you need to know about binary logs: how to check them, read them, manage them, and avoid common pitfalls.</p><hr><h3 id="what-are-binary-logs-in-mysql"><strong>What Are Binary Logs in MySQL?</strong></h3><p>Binary logs are <strong>transaction logs</strong> that contain a record of database operations. Unlike the general log or slow query log, the binary log only records events that modify the database.</p><p>They are used for:</p><ul><li><strong>Replication</strong>: To send changes from a master to a replica.</li><li><strong>Backup and recovery</strong>: To perform <strong>point-in-time recovery</strong> (PITR) after restoring from a backup.</li></ul><hr><h3 id="how-to-check-if-binary-logging-is-enabled"><strong>How to Check if Binary Logging is Enabled</strong></h3><p>To verify if binary logging is active on your MySQL server, run:</p><pre><code class="language-sql">SHOW VARIABLES LIKE 'log_bin';
</code></pre><p>A value of <code>ON</code> confirms that binary logging is enabled.</p><p>You can also inspect the path and filename prefix of the logs:</p><pre><code class="language-sql">SHOW VARIABLES LIKE 'log_bin_basename';
</code></pre><p>For logging format (e.g., <code>ROW</code>, <code>STATEMENT</code>, or <code>MIXED</code>):</p><pre><code class="language-sql">SHOW VARIABLES LIKE 'binlog_format';
</code></pre><hr><h3 id="listing-binary-log-files"><strong>Listing Binary Log Files</strong></h3><p>To list all existing binary log files:</p><pre><code class="language-sql">SHOW BINARY LOGS;
</code></pre><p>This shows the log file names and their sizes.</p><p>To see the <strong>current active binary log file</strong>:</p><pre><code class="language-sql">SHOW MASTER STATUS;
</code></pre><hr><h3 id="reading-binary-log-contents"><strong>Reading Binary Log Contents</strong></h3><p>You cannot read binary logs directly in SQL. Instead, use the <strong>mysqlbinlog</strong> command-line tool.</p><h4 id="example">Example:</h4><pre><code class="language-bash">mysqlbinlog /var/lib/mysql/binlog.000001
</code></pre><p>This will dump the contents to standard output.</p><h4 id="filtering-by-date-range">Filtering by date range:</h4><pre><code class="language-bash">mysqlbinlog --start-datetime="2025-06-25 00:00:00" \
            --stop-datetime="2025-06-25 23:59:59" \
            /var/lib/mysql/binlog.000001
</code></pre><h4 id="filtering-by-position">Filtering by position:</h4><pre><code class="language-bash">mysqlbinlog --start-position=107 --stop-position=512 binlog.000001
</code></pre><h4 id="to-apply-logs-to-a-mysql-server">To apply logs to a MySQL server:</h4><pre><code class="language-bash">mysqlbinlog binlog.000001 | mysql -u root -p
</code></pre><hr><h3 id="common-binary-log-file-path"><strong>Common Binary Log File Path</strong></h3><ul><li>Default location on Linux: <code>/var/lib/mysql/</code></li><li>Filename usually looks like: <code>binlog.000001</code>, <code>binlog.000002</code>, etc.</li></ul><p>Check your MySQL config file (<code>/etc/my.cnf</code> or <code>/etc/mysql/my.cnf</code>) for:</p><pre><code class="language-ini">[mysqld]
log-bin=mysql-bin
</code></pre><hr><h3 id="managing-binary-logs"><strong>Managing Binary Logs</strong></h3><p>Binary logs can <strong>consume a lot of disk space</strong> if not managed properly. Here are some key practices:</p><h4 id="1-set-expiration-policy">1. <strong>Set expiration policy</strong></h4><pre><code class="language-sql">SET GLOBAL binlog_expire_logs_seconds = 604800; -- 7 days
</code></pre><p>Or via configuration:</p><pre><code class="language-ini">expire_logs_days = 7
</code></pre><h4 id="2-manually-purge-binary-logs">2. <strong>Manually purge binary logs</strong></h4><pre><code class="language-sql">PURGE BINARY LOGS TO 'binlog.000010';
</code></pre><p>Or by date:</p><pre><code class="language-sql">PURGE BINARY LOGS BEFORE '2025-06-01 00:00:00';
</code></pre><h4 id="3-avoid-deleting-logs-used-in-replication">3. <strong>Avoid deleting logs used in replication</strong></h4><p>Always check slave status first:</p><pre><code class="language-sql">SHOW SLAVE STATUS\G
</code></pre><p>Look at the <code>Relay_Master_Log_File</code> before purging.</p><hr><h3 id="other-considerations"><strong>Other Considerations</strong></h3><ul><li><strong>Permissions</strong>: You need the <code>REPLICATION CLIENT</code> privilege to run <code>SHOW BINARY LOGS</code>.</li><li><strong>Log Rotation</strong>: MySQL creates a new log file automatically when the current file exceeds <code>max_binlog_size</code>.</li><li><strong>Binary log encryption</strong> is available from MySQL 5.7.11+ if enabled.</li><li><strong>Row-based logging</strong> is recommended for more accurate replication (especially with non-deterministic functions).</li></ul><hr><h3 id="use-cases-for-binary-logs"><strong>Use Cases for Binary Logs</strong></h3><ol><li><strong>Disaster Recovery</strong>: After restoring a full backup, replay binary logs to recover the latest state.</li><li><strong>Replication Troubleshooting</strong>: Inspect binlog to understand what changes were sent to replicas.</li><li><strong>Audit Trail</strong>: With some scripting, you can parse binlogs to detect what changes were made by whom (if you include user info in queries).</li></ol><hr><h3 id="finally"><strong>Finally</strong></h3><p>Managing binary logs effectively ensures better <strong>replication stability</strong>, <strong>faster recovery</strong>, and avoids <strong>disk space issues</strong>. By regularly inspecting and pruning your logs, you maintain a healthy MySQL instance. Remember to monitor your binlog size and frequency of changes, and always test your PITR process periodically.</p><p>If you're not using replication or PITR, you might consider disabling binary logs in non-critical environments to reduce I/O and disk usage. But for most production systems, they are <strong>indispensable</strong>.</p><h3 id="support-us">Support Us</h3>
