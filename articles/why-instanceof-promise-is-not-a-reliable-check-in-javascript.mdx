<p>When working with <strong>asynchronous programming</strong> in JavaScript, it is tempting to check whether a value is a <code>Promise</code> using <code>instanceof Promise</code>. At first glance, this seems logical—after all, promises are the foundation of async/await, so why not verify them directly?</p><p>But here’s the catch: <strong><code>instanceof Promise</code> is not a good or reliable check.</strong> Let’s dive into why, and what better practices you should adopt.</p><hr><h2 id="the-problem-with-instanceof-promise">The Problem with <code>instanceof Promise</code></h2><h3 id="1-cross-realm-issues">1. <strong>Cross-Realm Issues</strong></h3><p>JavaScript runs in different "realms"—for example, inside an <strong>iframe</strong> or a <strong>worker thread</strong>, the global <code>Promise</code> constructor is technically a different object.</p><p>This means:</p><pre><code class="language-js">iframePromise instanceof Promise // false
</code></pre><p>Even though it’s a perfectly valid promise, the check fails because it comes from a different global environment.</p><hr><h3 id="2-custom-thenables">2. <strong>Custom Thenables</strong></h3><p>The JavaScript spec defines promises in terms of <strong>thenables</strong>—objects with a <code>.then</code> method.</p><p>That means any object that implements <code>.then</code> can be awaited:</p><pre><code class="language-js">const thenable = {
  then(resolve) {
    resolve("Hello from a thenable!");
  }
};

await thenable; // Works fine!
</code></pre><p>Here, <code>thenable instanceof Promise</code> is <code>false</code>, but <code>await</code> doesn’t care—it just looks for a <code>.then</code> function.</p><p>This is why many libraries (e.g., <strong>Bluebird</strong>, ORM query builders, or custom async utilities) return thenables without necessarily being actual <code>Promise</code> objects.</p><hr><h3 id="3-spec-compliance">3. <strong>Spec Compliance</strong></h3><p>The ECMAScript specification explicitly states that both <code>await</code> and <code>Promise.resolve</code> will handle any <strong>thenable</strong>, not just native promises.</p><p>So by design, <strong>JavaScript treats awaitable values more broadly than just <code>Promise</code> instances</strong>.</p><hr><h2 id="a-better-way-duck-typing">A Better Way: Duck Typing</h2><p>Instead of relying on <code>instanceof</code>, the recommended approach is <strong>duck typing</strong>—checking whether the value behaves like a promise:</p><pre><code class="language-js">function isThenable(value) {
  return value != null &amp;&amp; typeof value.then === "function";
}
</code></pre><p>This works for:</p><ul><li>Native promises</li><li>Cross-realm promises</li><li>Custom thenables</li></ul><p>Essentially, if it walks like a duck (has a <code>.then</code> method), it’s treated like a duck.</p><hr><h2 id="other-considerations">Other Considerations</h2><h3 id="1-async-functions-always-return-promises">1. <strong>Async Functions Always Return Promises</strong></h3><p>Even if you return a primitive value inside an <code>async</code> function:</p><pre><code class="language-js">async function foo() {
  return 42;
}
</code></pre><p>Calling <code>foo()</code> will <strong>always</strong> return a promise. No need to check with <code>instanceof</code>.</p><hr><h3 id="2-avoid-over-checking">2. <strong>Avoid Over-Checking</strong></h3><p>In many cases, you don’t need to check at all. If you’re writing async code, you can often just <code>await</code> the value and trust the runtime:</p><pre><code class="language-js">const result = await maybePromise; 
</code></pre><p>If it’s not awaitable, you just get the value back immediately.</p><hr><h3 id="3-interoperability-across-libraries">3. <strong>Interoperability Across Libraries</strong></h3><p>When integrating with third-party libraries, <strong>don’t enforce <code>Promise</code> checks</strong> unless absolutely necessary. Some libraries intentionally return custom thenables for advanced scheduling, cancellation, or debugging features. Rejecting them because they fail an <code>instanceof</code> test could break compatibility.</p><hr><h3 id="4-error-handling">4. <strong>Error Handling</strong></h3><p>One subtle point: thenables might misbehave (e.g., badly written <code>.then</code> implementations). This is rare, but if you’re building low-level libraries, you should be aware that <strong>not all thenables are well-behaved</strong>. In such cases, defensive coding or normalization (<code>Promise.resolve(thenable)</code>) is a good idea.</p><hr><h2 id="the-takeaway">The Takeaway</h2><ul><li><strong>Don’t use <code>instanceof Promise</code></strong> as a general-purpose check.</li><li><strong>Do use duck typing</strong> (<code>typeof value?.then === "function"</code>) if you really need to distinguish thenables.</li><li>Often, you can <strong>skip the check entirely</strong> and just <code>await</code>—JavaScript will do the right thing.</li><li>Remember: <strong>async/await is about behavior, not about constructors.</strong></li></ul><hr><p>✅ <strong>In summary</strong>: The power of JavaScript’s async model comes from its <strong>flexibility with thenables</strong>, not just promises. By avoiding strict <code>instanceof</code> checks, you make your code more robust, interoperable, and future-proof.</p><h3 id="support-us">Support Us</h3>
