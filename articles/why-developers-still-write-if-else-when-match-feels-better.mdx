<p>When you first discover functional-style <strong>pattern matching</strong> in JavaScript or TypeScript — something like:</p><pre><code class="language-ts">match({
  A: (a) =&gt; handleA(a),
  B: (b) =&gt; handleB(b),
})(props)
</code></pre><p>—it’s hard not to wonder: <em>why are people still writing endless <code>if/else</code> or <code>switch</code> statements?</em> The elegance of a declarative <code>match</code> approach can feel like a breath of fresh air. But in practice, the story is a bit more nuanced. Let’s explore the reasons why <code>if/else</code> dominates, and where <code>match</code> truly shines.</p><hr><h2 id="the-comfort-zone-familiarity-and-readability">The Comfort Zone: Familiarity and Readability</h2><p>Most developers learned programming with <strong>imperative control flow</strong>: <code>if/else</code>, <code>switch</code>, <code>for</code>, <code>while</code>. These constructs are ingrained in almost every mainstream language.</p><ul><li><strong>Onboarding new developers:</strong> A junior engineer may find <code>if/else</code> easier to follow than an unfamiliar <code>match</code> abstraction.</li><li><strong>Code reviews:</strong> Teams often prioritize <em>clarity for the average reader</em> over elegance. A <code>switch</code> block is predictable; a custom <code>match</code> function needs explanation.</li></ul><p><strong>Readability is cultural.</strong> What looks clean and obvious to a functional programmer can look cryptic to someone without that background.</p><hr><h2 id="tooling-debugging-and-ide-support">Tooling, Debugging, and IDE Support</h2><p>Tooling ecosystems are still better aligned with traditional branching.</p><ul><li><strong>Autocomplete</strong> works naturally inside <code>if</code>/<code>switch</code> blocks.</li><li><strong>Linters and formatters</strong> enforce rules more consistently there.</li><li><strong>Debugging stack traces</strong> is often clearer: <code>if</code>/<code>else</code> shows a simple line number, while <code>match</code> may introduce anonymous functions and wrappers.</li></ul><p>When you’re working under tight deadlines, better tooling support often trumps elegance.</p><hr><h2 id="flexibility-complex-conditions">Flexibility: Complex Conditions</h2><p><code>match</code> works beautifully for <strong>discrete cases</strong> (enums, tagged unions, prop variants). But what about logic like:</p><pre><code class="language-ts">if (x &gt; 10 &amp;&amp; y &lt; 5 &amp;&amp; user.isActive) {
  …
}
</code></pre><p>Pattern-matching expressions can become awkward or verbose here. In contrast, <code>if/else</code> is designed for <strong>boolean logic without ceremony</strong>. This flexibility keeps it relevant.</p><hr><h2 id="performance-and-predictability">Performance and Predictability</h2><p>For small cases, performance differences are negligible. But in tight loops or hot paths:</p><ul><li><code>if/else</code> and <code>switch</code> can be optimized by JS engines into efficient jumps.</li><li><code>match</code> typically adds <strong>object lookups</strong> and <strong>function calls</strong>.</li></ul><p>Even if the real-world impact is small, some teams default to primitives for predictable performance.</p><hr><h2 id="the-weight-of-ecosystem-inertia">The Weight of Ecosystem Inertia</h2><p>Open any <strong>JavaScript tutorial</strong>, read most <strong>style guides</strong>, or look at <strong>Stack Overflow answers</strong>: you’ll find <code>if/else</code> everywhere. Developers stick with what’s “normal,” especially in team settings where unconventional code can raise eyebrows.</p><p>This inertia matters. Even if <code>match</code> is “better,” convincing a team to adopt a different mental model can be an uphill battle.</p><hr><h2 id="the-rise-of-pattern-matching-in-javascript">The Rise of Pattern Matching in JavaScript</h2><p>It’s worth noting that <strong>pattern matching is coming</strong> to JavaScript. TC39 (the committee behind JS standards) has a proposal for native syntax like:</p><pre><code class="language-js">match (value) {
  when { type: "A", data } =&gt; handleA(data),
  when { type: "B", data } =&gt; handleB(data),
  else =&gt; handleDefault()
}
</code></pre><p>When that lands, the argument for <code>if/else</code> weakens. But until then, most developers either don’t know about libraries like <strong>ts-pattern</strong>, or avoid them to reduce dependencies.</p><hr><h2 id="the-real-killer-feature-exhaustiveness-checking">The Real Killer Feature: Exhaustiveness Checking</h2><p>Here’s where <code>match</code> truly wins in TypeScript:</p><pre><code class="language-ts">type Shape = { kind: "circle", radius: number }
           | { kind: "square", size: number };

match(shape)
  .with({ kind: "circle" }, (c) =&gt; …)
  .with({ kind: "square" }, (s) =&gt; …)
  .exhaustive(); // ✅ ensures all cases are handled
</code></pre><p>With <code>if/else</code>, TypeScript won’t complain if you forget to handle <code>square</code>. With <code>match</code>, you get <strong>type-checked safety</strong>. This prevents entire classes of bugs.</p><hr><h2 id="other-considerations-you-might-be-missing">Other Considerations You Might Be Missing</h2><ol><li><strong>Team Culture:</strong> A “clever” <code>match</code> may get rewritten in review if your team values consistency over novelty.</li><li><strong>Error Handling:</strong> With <code>if/else</code>, it’s obvious where the <code>else</code> goes. With <code>match</code>, forgetting a default handler can cause runtime errors.</li><li><strong>Learning Curve:</strong> Not everyone on the team may understand functional abstractions, leading to accidental misuse.</li><li><strong>Future-Proofing:</strong> Betting on proposals or third-party libraries means you must maintain them. <code>if/else</code> will never disappear.</li></ol><hr><h2 id="so-which-one-should-you-use">So, Which One Should You Use?</h2><ul><li>Use <strong><code>if/else</code></strong> for <strong>quick, ad-hoc conditions</strong> or when working in codebases with mixed experience levels.</li><li>Use <strong><code>match</code></strong> when handling <strong>discriminated unions, enums, or structured props</strong>, especially in TypeScript where exhaustiveness matters.</li><li>Avoid dogma. Both tools have their place, and the best engineers know when to reach for each.</li></ul><hr><h2 id="finally">Finally</h2><p>Once you experience declarative <code>match</code>, <code>if/else</code> can feel primitive. But in the real world, factors like <strong>familiarity, tooling, flexibility, and inertia</strong> keep <code>if/else</code> alive.</p><p>The real shift will happen once <strong>JavaScript itself supports pattern matching</strong> natively. Until then, you’re likely to see both coexist — with <code>if/else</code> as the safe, universal option, and <code>match</code> as the more elegant but niche choice.</p><p><strong>Elegance vs. familiarity. Safety vs. simplicity.</strong> That’s the balance every developer has to strike.</p><h3 id="support-us">Support Us</h3>
