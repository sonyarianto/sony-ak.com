<p>In the world of JavaScript, there’s one value that consistently surprises both beginners and seasoned developers alike: <code>NaN</code>. At first glance, it might look like just another value in the <code>Number</code> type. But dig a little deeper, and you’ll realize it’s anything but ordinary.</p><p>Let’s start with something that <strong>baffles almost everyone</strong>:</p><pre><code class="language-js">console.log(NaN === NaN); // false
</code></pre><p>Wait, what?</p><p>How can something <strong>not be equal to itself</strong>? In every other case in JavaScript, if <code>x === x</code>, it’s true — but <code>NaN</code> breaks that logic.</p><h2 id="why-is-nan-not-equal-to-itself"><strong>Why Is NaN Not Equal to Itself?</strong></h2><p>This isn’t just JavaScript being weird — it’s actually <strong>by design</strong>, based on the <strong>IEEE 754</strong> floating-point standard. JavaScript uses this standard to represent numbers, and in that world:</p><blockquote><strong>"NaN is not equal to anything, including itself."</strong></blockquote><p>This is because <code>NaN</code> represents <strong>an invalid or unrepresentable number</strong>. For instance:</p><ul><li><code>0 / 0</code></li><li><code>Math.sqrt(-1)</code></li><li><code>parseInt("not-a-number")</code></li></ul><p>All produce <code>NaN</code>.</p><p>Imagine trying to compare two invalid results — should they be equal just because both are invalid? IEEE 754 says no. So JavaScript follows suit.</p><h2 id="then-how-do-you-check-for-nan"><strong>Then How Do You Check for NaN?</strong></h2><p>You can't rely on strict or loose equality (<code>===</code> or <code>==</code>). Instead, JavaScript gives us a better tool:</p><pre><code class="language-js">Number.isNaN(value); // ✅ Accurate
</code></pre><p>This function <strong>only returns true if the value is actually NaN</strong>, and not just some weird coercion like this:</p><pre><code class="language-js">isNaN("abc"); // true (⚠️ misleading)
Number.isNaN("abc"); // false (✅ correct)
</code></pre><p>So: <strong>Always use <code>Number.isNaN</code></strong> for reliability.</p><h2 id="but-why-is-typeof-nan-number"><strong>But Why is <code>typeof NaN === "number"</code>?</strong></h2><p>This confuses a lot of people too. If it’s "Not a Number", why is it a number?</p><p>Well, <strong><code>NaN</code> is a numeric value</strong>, just a <strong>special one</strong>. It’s still of type <code>"number"</code>, because it’s the result of an operation that should yield a number, but <strong>failed</strong>.</p><p>Think of it as:</p><blockquote>"It's supposed to be a number, but something went wrong."</blockquote><p>It’s like trying to divide by zero and getting a result that’s... well, undefined in math terms.</p><h2 id="real-world-pitfalls-of-nan"><strong>Real-World Pitfalls of NaN</strong></h2><p>One of the <strong>dangerous aspects</strong> of <code>NaN</code> is how it silently breaks logic when not handled properly.</p><h3 id="example-average-calculator">Example: Average Calculator</h3><pre><code class="language-js">function average(scores) {
  const sum = scores.reduce((a, b) =&gt; a + b, 0);
  return sum / scores.length;
}

average([]); // NaN — because 0 / 0
</code></pre><p>That may propagate and cause downstream bugs if you forget to check.</p><h3 id="example-filtering-nan-values">Example: Filtering NaN Values</h3><pre><code class="language-js">const data = [10, NaN, 15, NaN];
const clean = data.filter(n =&gt; !Number.isNaN(n)); // [10, 15]
</code></pre><h2 id="what-about-objectis"><strong>What About Object.is?</strong></h2><p>Here’s another lesser-known tip:</p><pre><code class="language-js">Object.is(NaN, NaN); // true
</code></pre><p>This method <strong>can</strong> distinguish <code>NaN</code> properly. It’s often used in polyfills or deep equality checks.</p><h2 id="in-summary"><strong>In Summary</strong></h2><ul><li><code>NaN === NaN</code> is <strong>false</strong> because of IEEE 754 — it’s by design.</li><li>Use <code><strong>Number.isNaN</strong></code>, not <code>isNaN</code>, to check for true <code>NaN</code>.</li><li><code>typeof NaN === "number"</code> because it <strong>is</strong> a numeric type — just an invalid one.</li><li>Use <code><strong>Object.is</strong></code> if you really want to compare two <code>NaN</code> values.</li><li>Always guard against <code>NaN</code> in mathematical logic to avoid silent bugs.</li></ul><h3 id="finally"><strong>Finally</strong></h3><p>In a language as quirky as JavaScript, <code>NaN</code> is a reminder that <strong>not all "numbers" behave like numbers</strong>. It's a symbol of failure in numeric computation — but understanding it helps you write <strong>safer, more robust code</strong>.</p><h3 id="support-us">Support Us</h3>
