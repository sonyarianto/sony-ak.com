<p>Upgrading to <strong>PHP 8.4</strong> brings a wave of performance improvements and cleaner language features. But along with that comes one of the most commonly encountered warnings developers now see:</p><blockquote><strong>Deprecated</strong>: Creation of dynamic property <em>SomeClass::$propertyName</em> is deprecated.</blockquote><p>If you’re seeing messages like this across your project — especially after upgrading from PHP 7.x or early 8.x — you’re not alone. This change touches a lot of legacy code written before strict property declarations became the norm.</p><p>Let’s dive deep into what’s going on, why it matters, and how to fix it <em>the right way</em>.</p><hr><h2 id="%F0%9F%A7%A0-what-are-dynamic-properties">🧠 What Are Dynamic Properties?</h2><p>In older versions of PHP, you could freely add properties to any object, even if the class didn’t declare them:</p><pre><code class="language-php">class User {}

$user = new User();
$user-&gt;name = 'Sony';  // ✅ Worked fine before PHP 8.2
</code></pre><p>This is called a <strong>dynamic property</strong> — a property created at runtime that doesn’t exist in the class definition.</p><p>It was convenient for quick prototypes, but in large codebases, it often led to <strong>typos</strong>, <strong>hard-to-track bugs</strong>, and <strong>unexpected behavior</strong>.</p><p>PHP’s internal engine also had to handle these ad-hoc properties dynamically, which introduced performance overhead.</p><hr><h2 id="%E2%9A%A0%EF%B8%8F-what-changed-in-php-82-%E2%80%94-and-why-it-matters-in-php-84">⚠️ What Changed in PHP 8.2 — and Why It Matters in PHP 8.4</h2><p>Starting in <strong>PHP 8.2</strong>, dynamic property creation was marked <strong>deprecated</strong>.<br>By <strong>PHP 8.4</strong>, the deprecation warning is far more aggressive — it will show up anywhere you try to set a property that doesn’t exist.</p><p>So if you have legacy classes like this:</p><pre><code class="language-php">class dataUsers {
    public function __construct() {
        $this-&gt;queryData = []; // ⚠️ Deprecated in PHP 8.4
    }
}
</code></pre><p>You’ll now get:</p><pre><code>Deprecated: Creation of dynamic property dataUsers::$queryData is deprecated
</code></pre><hr><h2 id="%E2%9C%85-the-proper-fix-explicit-property-declaration">✅ The Proper Fix: Explicit Property Declaration</h2><p>The modern PHP way is simple — <strong>declare all properties explicitly</strong> in your class.</p><p>Example:</p><pre><code class="language-php">class dataUsers {
    public array $queryData = [];

    public function __construct() {
        // no warnings
    }
}
</code></pre><p>This ensures:</p><ul><li><strong>Static analysis tools</strong> (like PHPStan or Psalm) can catch type issues.</li><li><strong>Better IDE autocompletion</strong> and refactoring.</li><li><strong>Faster runtime performance</strong> since properties are no longer dynamically bound.</li></ul><p>If you’re unsure about the type, you can use <code>mixed</code>:</p><pre><code class="language-php">public mixed $queryData;
</code></pre><hr><h2 id="%F0%9F%A9%B9-temporary-workaround-allow-dynamic-properties">🩹 Temporary Workaround: Allow Dynamic Properties</h2><p>If you’re maintaining a large legacy project and can’t refactor everything at once, PHP gives you a <strong>temporary escape hatch</strong>:</p><pre><code class="language-php">#[AllowDynamicProperties]
class dataUsers {
    // dynamic properties still allowed here
}
</code></pre><p>This attribute tells PHP:</p><blockquote>“I understand what I’m doing — don’t throw a deprecation warning for this class.”</blockquote><p>But this should be a <strong>short-term patch</strong>, not a permanent fix.<br>The PHP core team has hinted that <strong>dynamic property support will be completely removed in PHP 9.0</strong>.</p><hr><h2 id="%F0%9F%A7%B0-alternative-option-use-stdclass-for-dynamic-data">🧰 Alternative Option: Use <code>stdClass</code> for Dynamic Data</h2><p>If your class is really just a data bucket, consider using the built-in <code>stdClass</code> instead:</p><pre><code class="language-php">$user = new stdClass();
$user-&gt;queryData = [];
$user-&gt;name = 'Sony';
</code></pre><p>This approach is perfect for flexible objects that don’t require strict typing or methods.</p><p>However, avoid mixing <code>stdClass</code> and your domain models — it reduces clarity in large applications.</p><hr><h2 id="%F0%9F%94%8D-how-to-find-and-fix-all-dynamic-properties-in-your-project">🔍 How to Find and Fix All Dynamic Properties in Your Project</h2><p>To refactor confidently, you’ll want to <strong>locate all instances</strong> where dynamic properties are being used.</p><h3 id="1-use-grep-or-ripgrep">1. Use Grep (or Ripgrep)</h3><p>In Linux/macOS terminal:</p><pre><code class="language-bash">grep -r '\$this-&gt;' /path/to/your/project | grep -v 'public' | grep -v 'protected' | grep -v 'private'
</code></pre><p>This helps identify <code>$this-&gt;something</code> assignments that may not have been declared.</p><h3 id="2-use-phpstan-or-psalm">2. Use PHPStan or Psalm</h3><p>Run:</p><pre><code class="language-bash">vendor/bin/phpstan analyse src
</code></pre><p>These static analyzers can detect undeclared properties automatically.</p><hr><h2 id="%F0%9F%A7%A9-edge-cases-to-watch-out-for">🧩 Edge Cases to Watch Out For</h2><p>Here are some subtle scenarios where the warning might appear even if you think you’re safe:</p><h3 id="1-trait-assignments">1. <strong>Trait Assignments</strong></h3><p>If a trait assigns <code>$this-&gt;something</code> but the property isn’t declared in the consuming class, PHP will warn you.<br>✅ Fix: Declare the property in the main class.</p><h3 id="2-anonymous-classes">2. <strong>Anonymous Classes</strong></h3><p>Anonymous classes (like those created inline for callbacks or mocks) can still hit this issue:</p><pre><code class="language-php">$anon = new class {
    public function __construct() {
        $this-&gt;temp = 'hello'; // deprecated
    }
};
</code></pre><p>✅ Fix: Declare the property or use a <code>#[AllowDynamicProperties]</code> attribute.</p><h3 id="3-framework-magic">3. <strong>Framework Magic</strong></h3><p>Frameworks that rely on magic getters/setters (like Laravel’s Eloquent models) already handle this via <code>__get()</code> and <code>__set()</code>.<br>They typically use the <code>#[AllowDynamicProperties]</code> attribute internally — so you don’t need to worry unless it’s your own class.</p><hr><h2 id="%F0%9F%8F%97%EF%B8%8F-best-practices-moving-forward">🏗️ Best Practices Moving Forward</h2><ul><li><strong>Always declare your properties explicitly.</strong></li><li>Use <strong>typed properties</strong> (<code>int</code>, <code>string</code>, <code>array</code>, etc.) wherever possible.</li><li>Keep <code>#[AllowDynamicProperties]</code> only for legacy compatibility.</li><li>Run <strong>PHPStan or Psalm</strong> as part of your CI pipeline to catch issues early.</li><li>For data-only structures, prefer <strong>DTOs (Data Transfer Objects)</strong> over free-form classes.</li></ul><hr><h2 id="%F0%9F%92%A1-pro-tip-automate-the-fix">💡 Pro Tip: Automate the Fix</h2><p>If you have hundreds of classes, consider writing a simple script that:</p><ol><li>Scans all <code>.php</code> files.</li><li>Detects <code>$this-&gt;</code> assignments inside class bodies.</li><li>Inserts a declared property automatically if missing.</li></ol><p>There are already open-source tools like <strong>rectorphp/rector</strong> that can automate this refactor with predefined rules for PHP 8.2+ compatibility.</p><hr><h2 id="%F0%9F%9A%80-finally">🚀 Finally</h2><p>The <strong>deprecation of dynamic properties</strong> is not PHP being strict for no reason — it’s part of a bigger movement toward <strong>cleaner, safer, and faster code</strong>.</p><p>It pushes developers to write <strong>more predictable classes</strong>, improves static analysis, and reduces subtle runtime bugs.</p><p>So while the warning may feel annoying at first, treating it seriously now will save you from future pain — especially as PHP 9 approaches.</p><p><strong>Declare your properties, type them properly, and your codebase will thank you later.</strong></p><h3 id="support-us">Support Us</h3>
