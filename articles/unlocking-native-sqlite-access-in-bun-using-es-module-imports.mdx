<p>In recent updates, <strong>Bun</strong> has been gaining traction for its speed, simplicity, and first-class TypeScript support. But one feature that often flies under the radar—and frankly feels like magic—is Bun’s ability to <strong>import SQLite databases as native modules</strong> using the <strong>ES module import attribute</strong>.</p><p>This is not just syntactic sugar. It removes layers of boilerplate, simplifies local development, and encourages rapid prototyping for projects that need lightweight persistence without spinning up a full database server.</p><hr><h2 id="a-fresh-way-to-load-sqlite-in-bun"><strong>A Fresh Way to Load SQLite in Bun</strong></h2><p>Traditionally, accessing SQLite in Node.js requires setting up a client library like <code>better-sqlite3</code> or <code>sqlite3</code>, initializing a connection, and managing file paths. But with Bun, it’s this simple:</p><pre><code class="language-js">import db from "./mydb.sqlite" with { type: "sqlite" };

console.log(db.query("SELECT * FROM users LIMIT 1").get());
</code></pre><h3 id="let%E2%80%99s-break-it-down"><strong>Let’s break it down:</strong></h3><ul><li><code><strong>import db from "./mydb.sqlite"</strong></code>: This line tells Bun to treat the SQLite file as a module. The magic happens in the <code>with { type: "sqlite" }</code> attribute.</li><li><strong><code>db.query(...).get()</code></strong>: This is a <strong>synchronous query interface</strong>, powered internally by <strong>better-sqlite3</strong>, one of the fastest SQLite drivers for JavaScript.</li></ul><p>There’s no need to manually <code>open</code> the database, configure clients, or manage concurrency. You just import and query. It feels natural—like working with a native JavaScript object.</p><hr><h2 id="why-this-matters"><strong>Why This Matters</strong></h2><h3 id="1-zero-setup"><strong>1. Zero Setup</strong></h3><p>No need to <code>npm install</code> any database driver if you're working with SQLite. Bun <strong>bundles support out of the box</strong>.</p><h3 id="2-instant-readwrite-access"><strong>2. Instant Read/Write Access</strong></h3><p>For quick data operations, prototyping, or even production apps with simple needs, this approach is <strong>immediate and frictionless</strong>.</p><h3 id="3-first-class-typescript-support"><strong>3. First-Class TypeScript Support</strong></h3><p>Type safety applies just as well here. You can even wrap query results in custom utility functions or types if needed.</p><hr><h2 id="use-cases-where-this-shines"><strong>Use Cases Where This Shines</strong></h2><ul><li><strong>CLI Tools</strong>: You can persist settings or logs to a <code>.sqlite</code> file without setting up external dependencies.</li><li><strong>Prototypes or MVPs</strong>: Store users, sessions, or content locally during early stages.</li><li><strong>Offline-First Apps</strong>: Great for Electron/Bun desktop apps that need local persistence.</li><li><strong>ETL Pipelines</strong>: Use SQLite as a temporary processing stage before exporting to another service.</li></ul><hr><h2 id="things-you-might-miss-but-shouldn%E2%80%99t"><strong>Things You Might Miss (But Shouldn’t)</strong></h2><h3 id="%E2%9C%85-transactions">✅ <strong>Transactions</strong></h3><p>Bun’s <code>db</code> object supports <code>transaction()</code> blocks:</p><pre><code class="language-js">const insertUser = db.transaction((user) =&gt; {
  db.query("INSERT INTO users (name) VALUES (?)").run(user.name);
});
</code></pre><p>This guarantees atomic operations, which are especially important in batch inserts or updates.</p><hr><h3 id="%E2%9C%85-parameterized-queries">✅ <strong>Parameterized Queries</strong></h3><p>Always use placeholders to prevent SQL injection—even in local apps:</p><pre><code class="language-js">db.query("SELECT * FROM users WHERE email = ?").get("user@example.com");
</code></pre><hr><h3 id="%E2%9C%85-bundling-considerations">✅ <strong>Bundling Considerations</strong></h3><p>If you're bundling the project (e.g., for production), make sure your <code>.sqlite</code> file is included in the deployment. Use <code>bunfig.toml</code> to mark it as an asset:</p><pre><code class="language-toml">[assets]
include = ["mydb.sqlite"]
</code></pre><hr><h3 id="%E2%9C%85-file-location-and-portability">✅ <strong>File Location and Portability</strong></h3><p>Relative imports like <code>./mydb.sqlite</code> work great for dev, but be cautious about <strong>file paths</strong> when moving to production or cross-platform environments. Consider using an absolute path if needed, or a fallback strategy like:</p><pre><code class="language-js">import path from "path";
const dbPath = path.resolve(process.cwd(), "data/mydb.sqlite");
</code></pre><p>Unfortunately, this strategy won't work with the ES import attribute—you'd fall back to <code>better-sqlite3</code> in this case.</p><hr><h2 id="%E2%9A%A0%EF%B8%8F-limitations-to-be-aware-of">⚠️ <strong>Limitations to Be Aware Of</strong></h2><ul><li><strong>Only works in Bun</strong>: This is not standard ECMAScript, so it won’t work in Node.js, Deno, or browsers.</li><li><strong>Read/Write Locking</strong>: SQLite still uses file-level locking. Concurrent writes can block, although Bun manages this well.</li><li><strong>Not ideal for large-scale multi-user systems</strong>: SQLite is file-based, so if you're scaling to many concurrent users across multiple servers, it’s not the best choice.</li></ul><hr><h2 id="conclusion"><strong>Conclusion</strong></h2><p>Bun’s support for importing SQLite databases using ES module attributes is <strong>a breath of fresh air</strong> for developers who value simplicity and speed. It aligns perfectly with Bun’s goals of reducing friction, minimizing dependencies, and embracing native performance.</p><p>Whether you're building a tiny CLI, an offline-first app, or just need a fast way to persist data without extra setup, <strong>this feature is a gem worth knowing</strong>. And best of all? It just works.</p><p>So go ahead—ditch the boilerplate and start querying.</p><h3 id="support-us">Support Us</h3>
