<p>In the world of web development and server administration, security is never optional. One small misconfiguration could expose sensitive data, especially when using popular version control systems like <strong>Git</strong>. One such vulnerability is accidentally exposing the <strong><code>.git</code> directory</strong> on your public-facing server.</p><p>Fortunately, there's a <strong>simple yet powerful solution</strong> that can protect your project from this mistake:</p><pre><code class="language-apache">RedirectMatch 404 /\.git
</code></pre><h2 id="%F0%9F%94%92-why-git-should-never-be-public">🔒 Why <code>.git</code> Should Never Be Public</h2><p>The <code>.git</code> folder contains <strong>the entire history of your codebase</strong>. If exposed, attackers can:</p><ul><li><strong>Download the full source code</strong> including sensitive business logic or API keys.</li><li><strong>Enumerate commits</strong> to discover removed files or secrets.</li><li><strong>Check out previous versions</strong> or security patches.</li><li><strong>Identify team members</strong> from commit metadata (emails, names).</li></ul><p>Exposing this folder is the digital equivalent of leaving your master key taped to your front door.</p><hr><h2 id="%F0%9F%A7%BE-what-does-redirectmatch-404-git-actually-do">🧾 What Does <code>RedirectMatch 404 /\.git</code> Actually Do?</h2><p>This directive tells <strong>Apache</strong> to match any request that contains <code>.git</code> and immediately return a <strong>404 Not Found</strong> response. Here’s the breakdown:</p><ul><li><code>RedirectMatch</code> is a flexible redirect mechanism using regular expressions.</li><li><code>404</code> means “Not Found” – not just blocked, but pretending the resource doesn’t exist.</li><li><code>/\.git</code> is a regex that matches anything beginning with <code>.git</code> (like <code>/project/.git</code>, <code>/api/.git/config</code>, etc.).</li></ul><h3 id="%E2%9C%85-benefits">✅ Benefits:</h3><ul><li><strong>Lightweight</strong>: No need for complex rewrite rules or <code>.htaccess</code> gymnastics.</li><li><strong>Foolproof</strong>: Blocks the entire <code>.git</code> directory and subpaths.</li><li><strong>Safe</strong>: Doesn't rely on potentially incorrect directory permissions.</li></ul><hr><h2 id="%F0%9F%9B%A0%EF%B8%8F-where-to-place-this-rule">🛠️ Where to Place This Rule</h2><p>You can place this line in your:</p><ul><li><code>.htaccess</code> file (if <code>AllowOverride All</code> is enabled),</li><li>Apache virtual host config,</li><li>Global Apache configuration file (<code>httpd.conf</code> or <code>apache2.conf</code>).</li></ul><p><strong>Example for <code>.htaccess</code>:</strong></p><pre><code class="language-apache">&lt;IfModule mod_rewrite.c&gt;
    RedirectMatch 404 /\.git
&lt;/IfModule&gt;
</code></pre><hr><h2 id="%F0%9F%94%8E-other-security-considerations-you-might-be-missing">🔎 Other Security Considerations You Might Be Missing</h2><p>While blocking <code>.git</code> is crucial, it’s just the <strong>tip of the iceberg</strong>. Here are more <strong>folders and files you should secure or restrict</strong>:</p><h3 id="%F0%9F%A7%B7-other-common-sensitive-paths">🧷 Other Common Sensitive Paths:</h3><pre><code class="language-apache">RedirectMatch 404 /\.svn       # Subversion
RedirectMatch 404 /\.hg        # Mercurial
RedirectMatch 404 /\.bzr       # Bazaar
RedirectMatch 404 /\.env       # Laravel and other frameworks
RedirectMatch 404 /composer\.(json|lock)
RedirectMatch 404 /package\.json
RedirectMatch 404 /yarn\.lock
RedirectMatch 404 /config\.php
RedirectMatch 404 /php\.ini
RedirectMatch 404 /vendor
</code></pre><p>These often contain <strong>configuration</strong>, <strong>credentials</strong>, or <strong>libraries</strong> that should never be exposed publicly.</p><hr><h2 id="%F0%9F%93%8B-bonus-testing-your-setup">📋 Bonus: Testing Your Setup</h2><p>After applying these rules, test them:</p><pre><code class="language-bash">curl -I https://yourdomain.com/.git/config
</code></pre><p>You should see:</p><pre><code>HTTP/1.1 404 Not Found
</code></pre><p>If you still get a <code>200 OK</code> or see content, your protection <strong>is not working</strong>. Check:</p><ul><li>If <code>.htaccess</code> is enabled (<code>AllowOverride All</code>),</li><li>If Apache modules (<code>mod_alias</code>, <code>mod_rewrite</code>) are enabled,</li><li>If the server is Nginx (Apache rules don’t apply there).</li></ul><hr><h2 id="%F0%9F%A7%B1-nginx-equivalent">🧱 Nginx Equivalent</h2><p>If you're using Nginx instead of Apache, use this in your server block:</p><pre><code class="language-nginx">location ~ /\.git {
    return 404;
}
</code></pre><hr><h2 id="%F0%9F%A7%A0-finally">🧠 Finally</h2><p>Security is often a <strong>game of layers</strong>, and no single line of code will protect everything. But small lines like:</p><pre><code class="language-apache">RedirectMatch 404 /\.git
</code></pre><p>can <strong>dramatically reduce your attack surface</strong>. In today’s internet, <strong>assuming your server is safe by default is dangerous</strong>. Instead, take a proactive stance and close every loophole, starting with the low-hanging fruit.</p><hr><p><strong>Remember:</strong> <em>Security isn't just about hiding secrets—it's about making sure they were never exposed in the first place.</em> ✅</p><h3 id="support-us">Support Us</h3>
