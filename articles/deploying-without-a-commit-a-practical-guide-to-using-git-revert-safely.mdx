<p>In every development cycle, there are moments where you realize that <strong>one commit should not go into production yet</strong>. Maybe it introduces a half-finished feature, a bug, or something that needs business approval. The problem is, this commit is already merged into your main branch alongside other valuable changes.</p><p>How do you deploy everything <strong>except that one commit</strong>? The safest and most common answer is: <strong>use <code>git revert</code></strong>.</p><hr><h2 id="what-git-revert-really-does">What <code>git revert</code> Really Does</h2><p>When you run:</p><pre><code class="language-bash">git revert &lt;commit-hash&gt;
</code></pre><p>Git doesn’t remove the commit from history. Instead, it creates a <strong>new commit</strong> that applies the <em>reverse diff</em> of the targeted commit. The history stays intact, but the <strong>net effect on your codebase is as if that commit never happened</strong>.</p><p>Example:</p><pre><code>A -- B -- C -- D   (main)
</code></pre><p>If you revert commit <strong>C</strong>, you get:</p><pre><code>A -- B -- C -- D -- E
</code></pre><p>Where <strong>E</strong> is a new commit that undoes the changes from <strong>C</strong>.</p><p>This approach is different from <code>git reset</code> or <code>git rebase</code>, which rewrite history. <code>git revert</code> is <strong>non-destructive</strong> and safe for branches that are already shared with a team or remote repository.</p><hr><h2 id="deploying-without-a-commit">Deploying Without a Commit</h2><p>Let’s say you want to deploy the project <strong>without commit <code>9a2e6f69b8</code></strong>. Here’s a practical step-by-step workflow:</p><ol><li><strong>Build and deploy from this branch</strong><br>Your deployment now contains everything on <code>main</code>, except the effect of the reverted commit.</li><li><strong>After deployment</strong><br>You have options:<ul><li>If you later decide that you actually want the commit back, you can either:</li><li></li></ul></li></ol><p><strong>Cherry-pick the original commit</strong>:</p><pre><code class="language-bash">git cherry-pick 9a2e6f69b8
</code></pre><p><strong>Revert the revert</strong>:</p><pre><code class="language-bash">git revert &lt;revert-commit-hash&gt;
</code></pre><p>If you only needed this revert temporarily, just delete the branch:</p><pre><code class="language-bash">git checkout main
git branch -D deploy-without-9a2e6f69b8
</code></pre><p>Your <code>main</code> remains untouched.</p><p><strong>Revert the unwanted commit</strong></p><pre><code class="language-bash">git revert 9a2e6f69b8
</code></pre><p>This will create a new commit undoing the changes.</p><p><strong>Create a new branch for deployment</strong></p><pre><code class="language-bash">git checkout main
git pull origin main
git checkout -b deploy-without-9a2e6f69b8
</code></pre><hr><h2 id="when-to-use-git-revert-vs-other-methods">When to Use Git Revert vs. Other Methods</h2><ul><li><strong>Use <code>git revert</code></strong> when working on shared branches (<code>main</code>, <code>develop</code>) where history must remain untouched.</li><li><strong>Use <code>git reset</code> or interactive <code>git rebase</code></strong> only in local/private branches that no one else is using. These rewrite history and can cause problems if others already pulled the branch.</li></ul><hr><h2 id="additional-considerations">Additional Considerations</h2><ol><li><strong>CI/CD pipelines</strong>: If you have automated deployment pipelines, consider pushing the temporary branch (<code>deploy-without-xyz</code>) and pointing your pipeline at that branch. This prevents accidental deployment from <code>main</code>.</li><li><strong>Temporary vs. permanent exclusion</strong>: If the commit is permanently bad, revert it directly in <code>main</code>. If it’s only temporarily excluded, keep the revert isolated in a deployment branch.</li><li><strong>Testing after revert</strong>: Always rebuild and run tests locally after a revert. Sometimes, removing one commit can cause subtle issues if later commits depend on it.</li></ol><p><strong>Team communication</strong>: Make sure your teammates know why a commit was reverted. It’s often helpful to write a descriptive commit message like:</p><blockquote>Revert “Add booking type selection and validation to WDWBookingForm” — excluded from release due to pending QA.</blockquote><p><strong>Merge commits</strong>: If the commit you want to skip is a merge commit, you need to specify which parent to keep. Example:</p><pre><code class="language-bash">git revert -m 1 &lt;merge-commit-hash&gt;
</code></pre><p><code>-m 1</code> tells Git to keep the mainline parent branch.</p><hr><h2 id="best-practice-workflow">Best Practice Workflow</h2><ul><li><strong>Never deploy straight from <code>main</code> if you’re unsure</strong>.</li><li><strong>Create a deployment branch</strong>, revert the unwanted commits, and deploy from there.</li><li><strong>Keep <code>main</code> clean</strong>, so the whole team sees the full history as it happened.</li><li><strong>Use cherry-pick or revert-revert</strong> later to restore any excluded changes.</li></ul><hr><h2 id="finally">Finally</h2><p><code>git revert</code> is one of those underrated commands that saves you from messy history rewrites. By understanding how it works and when to use it, you can confidently deploy without a specific commit while keeping your team’s workflow smooth and history transparent.</p><p><strong>Key takeaway</strong>: <strong>Revert creates, reset destroys.</strong> If you want safety and traceability, always choose revert for shared branches.</p><h3 id="support-us">Support Us</h3>
