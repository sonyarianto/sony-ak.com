<blockquote><em>"We deployed our app using Next.js and Turbopack... and accidentally exposed our entire source code."</em></blockquote><p>That’s not clickbait. It’s happening.</p><p>If you’re experimenting with or already using <strong>Turbopack</strong>, the Rust-based successor to Webpack in the Next.js ecosystem, there’s something you need to know right now:</p><blockquote><strong>Turbopack currently always generates production sourcemaps for the browser — and they contain your actual source code.</strong></blockquote><h3 id="wait-what%E2%80%99s-a-sourcemap">Wait, What’s a Sourcemap?</h3><p>Sourcemaps are files that map your <strong>compiled code</strong> (the stuff browsers read) back to your <strong>original source code</strong>. They’re fantastic for debugging — especially in development.</p><p>But here’s the catch: in <strong>production</strong>, they can become a <strong>security risk</strong> if not handled properly.</p><hr><h3 id="the-real-risk-source-code-leaks-in-production">The Real Risk: Source Code Leaks in Production</h3><p>Here’s what’s really happening:</p><ul><li>Your app is deployed to production with <code>.map</code> files.</li><li>These sourcemaps contain your <strong>original code</strong>, including:<ul><li>Component logic</li><li>Business rules</li><li>Even developer comments</li></ul></li><li>Anyone who finds those <code>.map</code> files can <strong>read your code</strong> — right from the browser.</li></ul><p>This isn’t just a theoretical problem. We’ve seen:</p><ul><li>Leaked API keys embedded in client-side logic</li><li>Internal developer notes exposed in comments</li><li>Proprietary algorithms being copied</li></ul><hr><h3 id="why-this-is-happening-in-turbopack">Why This Is Happening in Turbopack</h3><p>Turbopack is still under <strong>active development</strong>. At the time of writing:</p><ul><li>It <strong>does not yet expose config options</strong> to disable or restrict sourcemap generation in production.</li><li>That means unless you intervene, <strong>your source will ship</strong> with your production build.</li></ul><hr><h3 id="how-to-fix-or-mitigate-it">How to Fix or Mitigate It</h3><p>While Turbopack doesn’t have a toggle yet, you can still protect yourself.</p><h4 id="1-strip-sourcemaps-before-deployment">1. <strong>Strip Sourcemaps Before Deployment</strong></h4><p>After running your build, delete all sourcemap files:</p><pre><code class="language-bash">find .next -name '*.map' -delete
</code></pre><p>Make this part of your CI/CD pipeline. It’s your last line of defense.</p><hr><h4 id="2-block-access-at-the-server-level">2. <strong>Block Access at the Server Level</strong></h4><p>If you’re serving your app through a custom server or reverse proxy (like Nginx), add a rule to <strong>deny <code>.map</code> files</strong>:</p><pre><code class="language-nginx">location ~* \.map$ {
    deny all;
}
</code></pre><p>For <strong>Vercel deployments</strong>, use <code>vercel.json</code>:</p><pre><code class="language-json">{
  "headers": [
    {
      "source": "/(.*)\\.map",
      "headers": [{ "key": "x-robots-tag", "value": "noindex" }]
    }
  ]
}
</code></pre><hr><h4 id="3-audit-your-production-builds">3. <strong>Audit Your Production Builds</strong></h4><p>Don't just assume everything is safe.</p><ul><li>Open your deployed site.</li><li>Open DevTools → <strong>Network</strong> tab.</li><li>Refresh and filter for <code>.map</code>.</li><li>If you see anything — <strong>take it down</strong> or block it.</li></ul><hr><h3 id="what-else-should-you-worry-about">What Else Should You Worry About?</h3><ul><li><strong>Error tracking tools</strong> (like Sentry) require sourcemaps. If you’re using them, make sure to <strong>upload sourcemaps privately</strong>, not serve them publicly.</li><li>Watch for <strong>API key exposure</strong> or <strong>comments</strong> in code. Sourcemaps often include more than you expect.</li><li>This also applies to <strong>private projects</strong>. Even internal dashboards can leak.</li></ul><hr><h3 id="the-bigger-picture">The Bigger Picture</h3><p>This isn't a "Turbopack is bad" post — quite the opposite. Turbopack is incredibly fast and promising.</p><p>But as developers, we must treat <strong>build tooling with respect</strong>, especially when it’s new. Assume nothing. Check everything.</p><hr><h3 id="finally">Finally</h3><p>If you’re pushing code to production, always ask:</p><blockquote>🔐 <strong>“Did I just give away more than I built?”</strong></blockquote><p>You might be surprised.</p><h3 id="support-us">Support Us</h3>
