<p>As our TypeScript codebases grow, <strong>clarity and consistency</strong> become more important than clever tricks. One underrated but impactful practice is how we <strong>define return types</strong>—or more accurately, when we should and when we shouldn't.</p><p>This article walks through my current recommendation (yes, it's changed a few times), and highlights some useful considerations that you might have overlooked.</p><hr><h2 id="%F0%9F%8E%AF-always-explicit-for-top-level-functions">🎯 Always Explicit for Top-Level Functions</h2><p>When you're writing a <strong>top-level function</strong>—especially one that’s exported or reused across multiple files—<strong>always declare the return type</strong>. This isn’t just for TypeScript. It’s for:</p><ul><li><strong>Human readers</strong> who want to understand what your function is supposed to do,</li><li><strong>Static analysis tools</strong> and <strong>AI assistants</strong> that can offer better support,</li><li><strong>Future-you</strong>, when you're trying to figure out why something is returning a weird value.</li></ul><pre><code class="language-ts">// ✅ Good
const getGreeting = (): string =&gt; {
  return "Hello";
};
</code></pre><p>Even though TypeScript can infer this, <strong>inference isn't documentation</strong>. Explicit return types act as contracts.</p><hr><h2 id="%F0%9F%8E%A8-skip-it-for-jsx-components">🎨 Skip It for JSX Components</h2><p>There’s one clear exception: <strong>React components</strong>. If your function is a component returning JSX, <strong>don't bother specifying the return type</strong>.</p><pre><code class="language-tsx">// ✅ Also Good
const HelloWorld = () =&gt; {
  return &lt;div&gt;Hello World&lt;/div&gt;;
};
</code></pre><p>In this case, the return type is always something React can render—JSX or <code>ReactNode</code>. Adding an explicit return type like <code>JSX.Element</code> or <code>React.ReactElement</code> often adds noise without much benefit.</p><p>Let the code speak for itself.</p><hr><h2 id="%F0%9F%A4%9D-helper-functions-inside-components-declare-it">🤝 Helper Functions Inside Components? Declare It.</h2><p>While we can skip return types for components, <strong>any helper function inside a component</strong> that performs logic (e.g., formatting data, calculations) <strong>should still declare its return type</strong>.</p><pre><code class="language-tsx">const UserCard = ({ name }: { name: string }) =&gt; {
  const formatName = (name: string): string =&gt; {
    return name.trim().toUpperCase();
  };

  return &lt;div&gt;{formatName(name)}&lt;/div&gt;;
};
</code></pre><p>This keeps the function <strong>self-describing</strong> and avoids hidden surprises, especially when logic becomes more complex over time.</p><hr><h2 id="%F0%9F%A7%AA-don%E2%80%99t-trust-typescript%E2%80%99s-inference-blindly">🧪 Don’t Trust TypeScript’s Inference Blindly</h2><p>Yes, TypeScript is smart. But relying too much on inference:</p><ul><li>Makes it harder to detect accidental return changes</li><li>Reduces IDE readability (you need to hover or peek definitions)</li><li>Can lead to <strong>wider-than-necessary return types</strong> (e.g., <code>string | undefined</code> when you expected <code>string</code>)</li></ul><pre><code class="language-ts">// ❌ Might return undefined, but you won't know unless you dig
const getName = (user: User) =&gt; user.name;
</code></pre><p>Be intentional. If you expect a string, say it:</p><pre><code class="language-ts">const getName = (user: User): string =&gt; user.name ?? "Anonymous";
</code></pre><hr><h2 id="%F0%9F%93%A6-use-void-or-promisevoid-for-side-effect-functions">📦 Use <code>void</code> or <code>Promise&lt;void&gt;</code> for Side-Effect Functions</h2><p>If your function performs a side effect and doesn't return anything meaningful, use <code>void</code> (or <code>Promise&lt;void&gt;</code> for async).</p><pre><code class="language-ts">const logMessage = (msg: string): void =&gt; {
  console.log(msg);
};

const syncData = async (): Promise&lt;void&gt; =&gt; {
  await someApiCall();
};
</code></pre><p>This avoids false assumptions that the function returns something usable.</p><hr><h2 id="%F0%9F%A7%BC-clean-code-is-clear-code">🧼 Clean Code Is Clear Code</h2><p>Here’s the bottom line:</p><ul><li>Use <strong>explicit return types</strong> for top-level and utility functions.</li><li>Skip them for <strong>JSX-returning components</strong> unless there's an edge case.</li><li>Be mindful of <strong>inferred types</strong>, and tighten them when necessary.</li><li>Use <code>void</code> to clearly signal non-returning behavior.</li><li>Consider your audience—<strong>teammates, future maintainers, and tools</strong>—when writing functions.</li></ul><p>By being intentional about return types, you improve not just correctness, but the <strong>readability, reliability, and maintainability</strong> of your code.</p><h3 id="support-us">Support Us</h3>
