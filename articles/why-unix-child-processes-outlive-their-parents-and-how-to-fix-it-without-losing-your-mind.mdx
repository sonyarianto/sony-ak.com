<p>One of the most frustrating surprises when working with Unix-based systems is discovering that <strong>child processes do not automatically die when their parent process exits</strong>.</p><p>If you’ve ever built a server, a background job runner, or any long-running application, you might have noticed this odd behavior: <strong>the parent crashes or closes, but the child keeps running happily in the background</strong>.</p><p>At first, it feels like a bug.<br>Later, you realize — <strong>it’s by design</strong>.</p><p>And if you want to change it, well... prepare to jump through a few flaming hoops.</p><hr><h2 id="why-child-processes-survive">Why Child Processes Survive</h2><p>Unix and Linux systems intentionally allow child processes to survive their parent’s death.<br>When the parent process exits, the child is simply <strong>re-parented to <code>init</code> (PID 1)</strong> or another "adopting" process.</p><p>This behavior is rooted in the <strong>Unix philosophy</strong>:</p><blockquote><strong>Processes are independent entities.</strong></blockquote><p>Killing a child just because the parent exited would be seen as overly aggressive. In the traditional Unix mindset, a child process might be doing important work that should <strong>outlive</strong> the parent — such as a shell session (<code>sshd</code>), a worker process, or a daemon.</p><p>In short:</p><ul><li><strong>Fault tolerance</strong>: Avoid collateral damage.</li><li><strong>Autonomy</strong>: Processes should manage themselves.</li></ul><hr><h2 id="but-in-real-life-we-often-want-them-dead">But in Real Life... We Often Want Them Dead</h2><p>Today, many systems are designed differently:<br>If the parent dies, <strong>the child should die too</strong>.</p><p>For example:</p><ul><li>A web server that spawns worker threads or processes.</li><li>A job runner that spawns background tasks.</li><li>A CLI tool that runs helper processes.</li></ul><p>When the parent crashes, <strong>leaving those children behind can create resource leaks, zombies, security risks, or broken behaviors</strong>.</p><p>Thus, it’s incredibly common that modern developers <strong>want the children to automatically terminate</strong>.</p><hr><h2 id="how-to-actually-kill-child-processes-when-parent-exits">How to Actually Kill Child Processes When Parent Exits</h2><p>Sadly, <strong>Unix doesn't offer a simple checkbox</strong>.<br>You need to do a little dance. Here are the main strategies:</p><hr><h3 id="1-use-prctlprsetpdeathsig-linux-only">1. Use <code>prctl(PR_SET_PDEATHSIG)</code> (Linux only)</h3><p>If you’re on Linux, you can ask the kernel to <strong>send a signal</strong> to the child when the parent exits.</p><p>Example in C:</p><pre><code class="language-c">#include &lt;sys/prctl.h&gt;
#include &lt;signal.h&gt;

void setup_pdeathsig() {
    prctl(PR_SET_PDEATHSIG, SIGTERM);
}
</code></pre><p>The child will receive <code>SIGTERM</code> when the parent dies.</p><p>✅ <strong>Advantages</strong>:</p><ul><li>Built-in.</li><li>Simple.</li></ul><p>❌ <strong>Drawbacks</strong>:</p><ul><li><strong>Linux-only</strong>.</li><li>You must call it <strong>immediately after fork()</strong>.</li><li>Some weirdness if reparenting happens.</li></ul><hr><h3 id="2-create-a-process-group-and-kill-the-group">2. Create a Process Group and Kill the Group</h3><p>You can create a <strong>new process group</strong> containing the parent and children, and kill the entire group if needed.</p><p>In a Bash script:</p><pre><code class="language-bash">#!/bin/bash

# Start a subshell with new process group
( 
  setsid your_child_program 
) &amp;
child_pid=$!

# Trap exit and kill group
trap "kill -- -$child_pid" EXIT

wait $child_pid
</code></pre><p>In C:</p><pre><code class="language-c">setpgid(0, 0); // Set self to be leader of a new group
...
kill(-getpgrp(), SIGTERM); // Kill whole group
</code></pre><p>✅ <strong>Advantages</strong>:</p><ul><li>Portable (works on Unix, Linux, macOS).</li></ul><p>❌ <strong>Drawbacks</strong>:</p><ul><li>If the parent crashes, <strong>trap may not fire</strong>.</li><li>You need careful process management.</li></ul><hr><h3 id="3-use-an-external-supervisor-like-systemd">3. Use an External Supervisor (like <code>systemd</code>)</h3><p>If you run your app as a service, you can let a <strong>supervisor like <code>systemd</code></strong> handle it.</p><p>Example in a systemd unit:</p><pre><code class="language-ini">KillMode=control-group
</code></pre><p>This ensures <strong>all processes</strong> in the service get killed when the service stops.</p><p>✅ <strong>Advantages</strong>:</p><ul><li>Rock-solid.</li><li>No code needed.</li></ul><p>❌ <strong>Drawbacks</strong>:</p><ul><li>Only works <strong>inside a systemd unit</strong>.</li><li>Not portable to ad-hoc running environments.</li></ul><hr><h3 id="4-write-a-watchdog-process">4. Write a Watchdog Process</h3><p>Another approach: spawn a lightweight <strong>watchdog</strong> that monitors the parent and kills the children if needed.</p><p>It’s basically:</p><ul><li>Fork a tiny monitor process.</li><li>Monitor parent PID (<code>getppid()</code>).</li><li>If parent PID changes to 1 (<code>init</code>), kill children.</li></ul><p>✅ <strong>Advantages</strong>:</p><ul><li>Portable.</li></ul><p>❌ <strong>Drawbacks</strong>:</p><ul><li>More complexity.</li><li>Watchdog must be carefully written.</li></ul><hr><h2 id="sample-illustration-a-real-scenario">Sample Illustration: A Real Scenario</h2><p>Imagine you're building a simple API server:</p><pre><code class="language-plaintext">api-server
 ├── spawn worker 1
 ├── spawn worker 2
 ├── spawn worker 3
</code></pre><p>If the <code>api-server</code> crashes, you don't want <code>worker 1</code>, <code>worker 2</code>, and <code>worker 3</code> lingering around.</p><h3 id="without-any-extra-logic">Without any extra logic:</h3><ul><li><code>api-server</code> crashes.</li><li>Workers stay alive, consuming memory and CPU.</li></ul><h3 id="with-a-process-group">With a process group:</h3><ul><li><code>api-server</code> starts a new group.</li><li>On crash (or via a signal), the entire group can be killed cleanly.</li></ul><h3 id="with-prctl">With <code>prctl()</code>:</h3><ul><li>Each worker knows to self-destruct if it notices the parent is dead.</li></ul><hr><h2 id="other-important-considerations">Other Important Considerations</h2><ul><li><strong>What about daemons?</strong> Some children are intentionally designed to "daemonize" (detach completely). Those will need a different treatment if you still want to control them.</li><li><strong>Zombie Processes?</strong> Even after a child dies, if the parent doesn’t <code>wait()</code> on it, it may leave a <strong>zombie process</strong>. Be sure to reap your children properly.</li><li><strong>What if the parent crashes hard (e.g., <code>kill -9</code>)?</strong> Some solutions (like <code>trap</code>) won't catch that. Kernel-level options like <code>PR_SET_PDEATHSIG</code> work better for hard crashes.</li></ul><hr><h2 id="finally">Finally</h2><p>It’s ironic:<br><strong>A behavior that often makes sense in theory causes endless headaches in practice.</strong></p><p>Unix intentionally keeps child processes alive after the parent dies to preserve independence.<br><strong>But in today’s world, you often need the opposite.</strong></p><p>Whether you use <code>prctl()</code>, process groups, systemd, or watchdogs — just know that <strong>making children die with their parent is something you have to explicitly build</strong>.</p><p>And yes, you will have to do a few backflips.<br>But at least now, you know exactly <strong>which circus act</strong> you need to perform.</p><h3 id="support-us">Support Us</h3>
