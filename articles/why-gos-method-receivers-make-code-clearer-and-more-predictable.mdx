<p>One of the most <strong>elegant design choices</strong> in Go is how it handles methods. If you've ever worked with object-oriented languages like Java or PHP, you might be used to methods living inside a class. In Go, there's <strong>no <code>class</code> keyword</strong>, but you can still attach methods to types using <strong>receivers</strong> — and honestly, it's refreshing.</p><p>Let’s break down what that means and why many Go developers (myself included) find it <strong>simple, clean, and powerful</strong>.</p><hr><h2 id="%F0%9F%94%B9-what-is-a-receiver-in-go">🔹 <strong>What is a Receiver in Go?</strong></h2><p>In Go, you can define a function that <strong>belongs to a type</strong> using a <strong>receiver</strong>. This receiver appears between the <code>func</code> keyword and the function name.</p><p>Here’s a simple example:</p><pre><code class="language-go">type User struct {
	Name string
}

func (u User) Greet() string {
	return "Hello, " + u.Name
}
</code></pre><p>In this case:</p><ul><li><code>User</code> is a struct.</li><li><code>(u User)</code> is the <strong>receiver</strong>.</li><li><code>Greet()</code> is the method tied to <code>User</code>.</li></ul><p>You're essentially saying: <strong>“This function Greet() belongs to the type User.”</strong></p><p>When calling it:</p><pre><code class="language-go">user := User{Name: "Sony"}
fmt.Println(user.Greet()) // Hello, Sony
</code></pre><hr><h2 id="%F0%9F%94%B8-value-vs-pointer-receivers">🔸 <strong>Value vs Pointer Receivers</strong></h2><p>Go gives you a choice: <strong>value receiver</strong> or <strong>pointer receiver</strong>. This is where Go shows its clarity.</p><ul><li><strong>Value receiver</strong> (<code>u User</code>) receives a copy. Changes inside the method do <strong>not</strong> affect the original.</li><li><strong>Pointer receiver</strong> (<code>u *User</code>) works with the original value. It <strong>can modify</strong> the actual struct.</li></ul><pre><code class="language-go">func (u *User) ChangeName(newName string) {
	u.Name = newName
}
</code></pre><p>Usage:</p><pre><code class="language-go">user.ChangeName("Arianto")
fmt.Println(user.Greet()) // Hello, Arianto
</code></pre><p>This flexibility is powerful and <strong>explicit</strong> — you know exactly what the method is doing.</p><hr><h2 id="%E2%9C%85-why-its-clear-and-predictable">✅ <strong>Why It's Clear and Predictable</strong></h2><p>Here’s why many Go developers love this approach:</p><ul><li><strong>You know where the method belongs.</strong> There’s no guessing — just look at the receiver.</li><li><strong>No hidden <code>this</code> or <code>self</code>.</strong> It’s just a parameter with a name you choose (<code>u</code>, <code>t</code>, anything).</li><li><strong>Encourages composition over inheritance.</strong> Go favors defining small types with clear responsibilities.</li><li><strong>Go automatically handles calling methods on pointers or values</strong> in many cases, making usage seamless.</li></ul><hr><h2 id="%F0%9F%A7%A0-additional-considerations">🧠 <strong>Additional Considerations</strong></h2><ul><li>If your method needs to <strong>modify</strong> the receiver or <strong>avoid copying large structs</strong>, use a <strong>pointer receiver</strong>.</li><li>If your method is <strong>read-only</strong>, and the struct is small, a <strong>value receiver</strong> may be better and simpler.</li><li>Go does <strong>not support method overloading</strong>, so each method tied to a type must have a unique name.</li><li>Unlike OOP languages, Go’s method sets control <strong>interface satisfaction</strong> — only methods with pointer receivers can be called on pointers, not on values (and vice versa).</li></ul><hr><h2 id="%F0%9F%93%A6-full-example-for-reference">📦 Full Example for Reference</h2><pre><code class="language-go">package main

import "fmt"

type User struct {
	Name string
}

func (u User) Greet() string {
	return "Hello, " + u.Name
}

func (u *User) ChangeName(newName string) {
	u.Name = newName
}

func main() {
	user := User{Name: "Sony"}
	fmt.Println(user.Greet()) // Hello, Sony

	user.ChangeName("Arianto")
	fmt.Println(user.Greet()) // Hello, Arianto
}
</code></pre><hr><h2 id="%F0%9F%8F%81-finally">🏁 Finally</h2><p>Go’s method receiver model may look different at first, but once you get it, it’s <strong>easy to reason about</strong>, <strong>less magical</strong>, and <strong>surprisingly expressive</strong>. Whether you’re writing libraries, services, or even CLIs, <strong>you always know what’s happening</strong> — and that’s a huge win for maintainability and readability.</p><p>Next time you define a function in Go, ask yourself:<br><strong>“Should this really be tied to a type?”</strong><br>If yes, then it’s time to use a receiver.</p><h3 id="support-us">Support Us</h3>
